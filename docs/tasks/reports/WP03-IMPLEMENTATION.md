# WP03 — Implementation report

Branch `wp/03` · Contract C3 (owner) · Date 2026-10-16

## 1. Summary

WP03 delivers four things:
- **`protocol/README.md`**: the normative spec of relay UDP protocol v1, marked **PROPOSAL v1 — agree with G0 firmware before flight**.
- **A standard-library Python reference implementation**:
  - `gcs/vtolgcs/protocol.py`: CRC-16, the four UDP messages, channel packing and scaling.
  - `gcs/vtolgcs/crsf.py`: streaming parser, builders, telemetry decoders, the extended-frame parameter protocol and flight-mode interpretation.
- **`gcs/tools/bridge_sim.py`**: a UDP bridge simulator. It covers the state machine, validation, both camera policies with read-back, 10 Hz status with an RTT echo, latency, jitter and loss injection, a simulated client with CRSF telemetry, optional fake video, and an optional fake-module `crsf_pass`.
- **`protocol/test-vectors.json`**: byte-exact vectors for every message, decoder, builder and malformed case, regenerated by `gcs/tools/gen_test_vectors.py`.

Every CRSF field layout was read from primary source files fetched at pinned commits, and is cited in the `crsf.py` module docstring and in each decoder's docstring:
- Betaflight `41a5b43379f0176c838c181e7c735c1e9e8767ab`
- ExpressLRS `dd96654519249798707f011b7c79236350f246f8`
- EdgeTX `65db64b4890c399b8fcc9cc6a3d002c2b86e4706`

Independent cross-checks against third-party vectors:
- EdgeTX's channel-packing gtest bytes;
- EdgeTX CRC-8 and timing-frame bytes;
- EdgeTX parser streams;
- EdgeTX CRC table rows;
- the CRC catalogue check values.

**302 pytest tests pass.**

## 5. Deviations / contract issues

**Files outside the owned list** (each minimal):
- `gcs/tools/gen_test_vectors.py`: needed so the vectors can be regenerated and checked (`--check`); the firmware team needs this too.
- `gcs/conftest.py`: puts `gcs/` and `gcs/tools/` on `sys.path`, so `python -m pytest gcs` works from the repo root without installing.
- `gcs/tests/_vectors.py`: a shared JSON loader for the tests.
- `gcs/.gitignore`: keeps `__pycache__` and `.pytest_cache` out of git. The root `.gitignore` only covers `relay/`.

**Contract C3 issues and decisions:**

1. **µs → CRSF formula.** The C3 formula maps **988 µs to 173, not 172**; 172 is 987.5 µs. EdgeTX uses the same 1.6 slope, so I kept the formula exactly as written and documented the difference (README §4). PM: accept, or change C3 to ELRS's `fmap(172..1811 → 988..2012)`.
2. **`rx_bad_crc` is overloaded.** v1 has no counters for wrong version, bad magic, length or source IP. I defined `rx_bad_crc` as "rejected by format checks" (magic, version, length, CRC). Source-IP rejects are logged but not reported. Suggested for v2: per-cause counters and `rx_bad_src`.
3. **`sync_period_x10us` / `sync_offset_x10us`.** Interpreted as 0.1 µs units (µs × 10), the unit the ELRS 0x3A frame uses. 0 means no timing frame seen. Documented.
4. **`fw_ver` encoding** was undefined. Proposed `(major << 8) | minor`, with `fw_ver_str()` for C2's `bridge.fw_version` string.
5. **Additions to C3, all marked PROPOSAL in the README:**
   - an extra `status` on every state entered, so the instantaneous FAILSAFE is visible to the GCS;
   - a `seq` re-baseline in WAIT_GCS, so a restarted GCS app is not rejected for up to 2³¹ packets;
   - a definition of "consecutive" (any reject, or a gap > T_hold, restarts the count);
   - validation order magic → ver → length → CRC (version before length so a future size change still counts as a version mismatch);
   - reserved flag bits ignored on receive.
6. **Forwarding rule.** The relay design says the G0 "handles frames addressed to 0xEA". But the ELRS parameter replies (0x29, 0x2B, 0x2E) are addressed to 0xEA, and the GCS needs them for plan §7.7. Proposed rule: forward everything except 0x3A timing frames. Firmware must agree.
7. **Corrections to the relay design from primary sources:**
   - The 0x3A rate and offset are **big-endian** (`htobe32`, ELRS `CRSFHandset.cpp`), in 0.1 µs, and the offset already includes ELRS's −100 µs margin.
   - EdgeTX starts the ModelID frame with **0xC8**, while the relay design has 0xEE. ELRS accepts both and does not check the inner 0xBA CRC; our builder keeps 0xEE per the design.
   - The 24-byte RC frame makes ELRS take the arm state from **CH5**.
8. **0x09 baro altitude has two encodings in the primary sources:**
   - Betaflight: 3 bytes, with the vertical speed as an i8 log-packed value;
   - the ELRS struct: 4 bytes, with the vertical speed as i16 cm/s.

   The decoder selects by length and reports `vspd_format`.
9. **R5 gaps (cannot be confirmed from source, or not implemented):**
   - ELRS `int16ParameterToArray` `memcpy`s host-order `uint16`s. The Lua reader reads them big-endian, and I followed the Lua. Real 16-bit parameters should be checked on a module.
   - FLOAT is parsed per the Lua, but ELRS `sendParameter` never sends FLOAT, so there is no live example.
   - Not decoded: 32/64-bit integer types, VTX (15) and the 0x2E ELRS status frame. ELRS does not send the first two; 0x2E was not required.
   - The COMMAND step handshake (CLICK → EXECUTING → ASK_CONFIRM …) is only encoded and decoded. Driving it is WP08's job.
10. **Simulator assumption.** In the simulator the client's CRSF telemetry keeps flowing after the bridge goes silent, so `!FS!` → `RTH` is observable. Whether a real ELRS TX module keeps the link and telemetry up when its handset input stops is **unknown** (relay design risk table). If it does not, the GCS will not see `!FS!` over telemetry, and its **"telemetry stale" alarm** becomes the primary indicator. WP08 should not rely on `!FS!` arriving.
11. **Simulated client arming.** It arms only after CH5 has been seen low (arm-switch cycling, as in Betaflight). A GCS that starts with the arm switch high will not see the client arm.
